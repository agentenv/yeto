## Decisions

1. **Remove only the signature and the key. Keep the structure checks.** The field set, status enum, and reward range check in `_validated` stay. Reason: they guard against code errors, not attacks.
2. **Raise the evidence schema to 3.** The schema 3 outcome hash is `hash(domain, canonical_outcome)` and has no mac. Writing uses only 3. Reading 1 and 2 follows D2.
3. **Metadata key names.** Keep `OUTCOME_KEY` unchanged, to avoid affecting replay tools. Delete `MAC_KEY`. When reading, ignore an old mac field.
4. **Key environment variables.** Remove them from the pass-through list and from the preflight check. Do not add a check that fails when they are set.
5. **Do not touch the island HMAC.** The HMAC in `syncer/src/elastic.rs`, `main.rs`, `server.rs` and in the Python files `elastic_client.py`, `protocol.py` is out of scope for this change.
6. **Order of work.** Step 1: remove the reward signature and raise the evidence schema. Step 2: handle the credential guard according to the D1 result (recommended: move it out of this change).

## Risks

- A replay tool may deduplicate or compare by mac. After the schema raise, it would treat old and new evidence as different. Mitigation: replay comparison compares only `reward_contract_hash` and the canonical outcome. Whether any tool compares by mac is **unverified**. During implementation, check `scripts/` and `tools/` with grep.
- Running in parallel with rl-code-quality-cleanup phase 4 may cause conflicts. Mitigation: merge this change first.

## Implementation record (2026-10-13, branch s23-t8, commit b62e2426)

1. **Schema 3 layout.** Schema 3 keeps the layered layout of schema 2 (active-token, compaction segment fields, `evidence_kind`). There is one difference: the outcome hash and trajectory_id no longer mix in the mac, and they use new hash domain names (`yeto-trajectory-id-v3`, `*-evidence-v2`, `yeto-trajectory-batch-v3`).
2. **Writing uses only 3.** `build_trajectory_batch_evidence` drops the `schema_version` parameter, and the result is always 3. Before, SecRLEnv flat samples wrote schema 1. Now they also write schema 3. Without a loss_mask, the active-token count equals the response length, so trained_tokens does not change. With a loss_mask, trained_tokens is now counted by active-token. So when you compare trained_tokens of a schema 3 run (and `rl/action_tokens`, which accumulates from it) with a schema 1 run, you must note the change of basis: the old value counts the response length, and the new value counts the tokens that the loss_mask selects.
3. **Reading 1 and 2.** When reading, check the field structure and the batch hash, and do not verify the mac (D2). Tests use real files generated by the f2db57f8 code (`tests/fixtures/trajectory_evidence/`, with the generator script in the same directory). The batch hash domain name for reading schema 2 stays `yeto-trajectory-batch-v2`.
4. **The startup context is still bound to 1 or 2.** This value is only a layout label from signing time (`sao_streaming_runtime.py` now has a comment; the test `test_context_schema_label_2_still_writes_trajectory_evidence_schema_3` locks in "context writes 2, actual output is 3"). `trajectory_evidence.schema_version` in the SAO context takes part in `sao_context_sha256`. To keep this hash unchanged, the value in the startup context does not change. `rollout_legacy_port` only checks that it is bound, and no longer uses it to choose the output layout.
5. **Function renames.** `build_signed_metadata` is renamed to `build_outcome_metadata`. `sign_outcome`, `validate_hmac_key_source`, `MAC_KEY`, `hmac_key_env_names`, `assert_no_reward_key`, and `scrubbed_environment` are removed. The names `verified_outcome`/`verify_outcome` stay, and their meaning is now "structure check".
6. **secrlenv group key.** The group key of `check_group` used the mac to tell apart different evidence at the same index. It now uses the canonical outcome.
7. **Unchanged hashes.** The composition of `BackendIdentity`, `session_contract_hash`, `lr_schedule_sha256`, the algorithm hash, and `training_contract_hash` is unchanged. Note: `reward_contract_hash` is the sha256 of the reward source files. `reward.py` changed, so its value changes for new runs. Its composition does not change. The three source pin values were recomputed with the file changes.
8. **Island HMAC.** `YETO_ISLAND_HMAC_KEY` and the syncer seal/open are unchanged (confirmed with grep).
9. **Reward-function evidence kind (2026-10-14, P0-1.11 GPU run, third stage).** The dense full-parameter island hard-coded the `secrlenv` evidence kind, so a GSM8K island failed its first round with `UntrustedOutcome`. The main agent chose option A: add the kind `reward-function`. Its outcome is the prompt (task id `prompt-sha256:<hex>`), the logical sample (episode id `sample:<index>`), and `sample.reward`; its outcome hash uses the domain `yeto-reward-function-evidence-v1`. The island chooses the kind from `--reward-function` (`island_entry._trajectory_evidence_kind`). Meaning change: evidence is either a trusted grader verdict or a reward function output. A sample that carries a grader verdict is rejected as `reward-function` evidence, so a grader run cannot fall back to the weaker kind. The schema number does not change: the kind is already part of the schema 3 and 4 batch hash.
