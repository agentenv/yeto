## Goals / Non-Goals

Goals: follow the PM order. Delete the legacy engine. One bridge, one definition of weights and staleness. One resume abstraction. The other convergence work rolls forward. Every PR causes zero change in training behavior and can be rolled back on its own.

Non-Goals: changing training numerics, changing scheduling semantics, changing external CLI semantics (except deleting the legacy options and the old import paths), Ascend, boat.dev.

The elastic controller copies and writes the manifest inside the record lock and commits outside the lock. A commit failure only records `commit_error`. The critic backend only provides the layout. Its save happens inside the trainer cut and does not go through `save(cut)` on its own.
8. **Algorithm/reward/config convergence**: for each item, cross-check first and merge after (Decision 9). The config schema has `yeto/rl/engine/run_flags.py` as the only source (P0-4.7-Q1, decided 2026-10-13: do not put it in `run_config.py`, which only parses). It is split per P0-4.7-Q2. Neutral flags are in `yeto/rl/engine/run_flags.py` (no backend name may appear in the file, and a test checks this). Miles/SGLang/Megatron flags and all internal flags of the island entry are in `yeto/rl/adapters/miles/run_flags.py`, registered through the `run_flags` role of `backends`. Each flag is defined once and grouped by theme (`THEMES` sets the help order). The RL group of the CLI and the parser of island_entry are generated with `add_rl_flags(parser, layer)`. The check table of the launcher uses `rl_option_pairs(...)`. The forward table uses `rl_forward_pairs(...)` (it checks both the CLI layer and the island layer, so a rename fails at import time). A test scans the `--...` literals in the launcher. A literal that is in neither the island schema nor the CLI schema can only be a registered non-RL flag (syncer, docker, git and so on). A difference between the island side and the CLI can only be written in the `island={...}` of a schema entry and must be registered in a test. The argument list was generated first and diffed, and the switch was made only when the difference was zero. The recommend flags and the W&B flags are still added by their own registration hooks. Island contract hash (4.8a, 2026-10-13): `island_contract_sha256(backend identity, learning-rate plan, algorithm spec)` moves to the v2 domain. The three items are concatenated in order and then hashed with sha256. An item that is not declared uses a placeholder of 32 zero bytes. When all three are undeclared (the learning-rate plan and the algorithm spec are both None), the value still equals the backend identity itself. The island-side algorithm spec hash is `AlgorithmSpec.sha256()`, which is the canonical JSON of the spec. It does not contain placement abilities such as `with_partitioned_serial`, so a colocated island and a fixed-partition island have the same contract (P4-Q4). The three sync bridges all call `config_island_contract_sha256(config)` to compute the contract, and none writes its own copy. All old contract values change. An old test run cannot be resumed (P0-D5 accepted). A value pinned by `--rl-island-contract-sha256` must be recomputed with the new algorithm. W&B, exporter, finalisation, env scrubber (4.8b, P0-4.8-Q1, decided 2026-10-13): verified, not merged. Reasons: `wandb_tape.py` and `rl/wandb_rl.py` both import `wandb_logger.py`, which is reuse. `export.py` (syncer binary checkpoint to HF) and `rl/export.py` (RL-AVG checkpoint to PEFT) have different input formats and uses. `budget_finalization.py` calls `finalization.py`. `rl/eval/rlf_baseline.py` already reuses `scrub` of `rl/rlf/modal.py`, and the child-process env filter `scrubbed_environment` is deleted by P2.     - The trajectory evidence is written by the ports rollout hook. `record_trained_groups` runs after the final loss mask and binds the batch of this round with the `yeto:<version>:<weight hash>` published by the driver. The function that writes evidence is in `adapters/miles/full_parameter/evidence.py`. The rollout function of the ports island is still `rollout_legacy_port.generate_rollout`, and it no longer writes evidence (before, it wrote once before filtering, which duplicated the hook). The hook is the only write point, once per round.
    - Layering: `yeto/rl/sao_streaming_runtime.py` does only the neutral contract load and check (`SaoRoleContract`, looked up by role name). `adapters/miles/full_parameter/sao_binding.py` turns it into a two-role `FullParameterSyncConfig`, checks the Miles arguments and binds. The island entry builds the sync config right after loading, so a role pairing error is still reported before any GPU work. The v1 contract schema is no longer written by anyone and is deleted.
    - Launcher (second part): `--rl-sync-preset sao-streaming-full --rl-sao-contracts <manifest>`. The manifest is written by `build_tbench21_sao_streaming_contracts.py finalize` and freezes the syncer semantic config. The launcher adopts this config and starts two syncers, actor and critic, by algorithm role (`role_syncer_commands`). It checks that the config hash it renders equals the frozen value, and that the role ports in the contract equal the launch ports. Each island receives its own contract path, contract SHA256 and context SHA256.
    - The rejection of `--rl-max-policy-age > 0` applies to all full-parameter islands (dense-full and SAO), not only SAO. P0-S lifts it.
    - The `base_policy_hash` of the receipt is unified to the slice identity (`policy_hash`), which equals the weight fingerprint published by the driver. The old special case of the SAO content_hash is deleted. An old SAO test run cannot be resumed (same as P0-D5).
    - P0-S status (code read on 10-13):
      1. The ports LoRA path already has a neutral limit `--rl-max-policy-age N`. On the Miles side N is at most 1, and `--partial-rollout` continues unfinished groups (tokens across versions are corrected with TIS). This is not an overlap of rollout and training: the driver still runs serially as "publish v_r, generate r, train r".
      2. The full-parameter path (dense, SAO) still requires strict equality. The trajectory evidence of each round has only one `behavior_policy_hash`. In the envelope, `behavior_policy_version` is fixed to equal rollout_id. `record_local_round` requires it to equal the anchor. A mixed-version batch needs a new evidence format (each trajectory records its own version), and this changes the batch hash that enters the receipt. This time, full-parameter islands explicitly reject `--rl-max-policy-age > 0`.
      3. The native Miles fully_async (`FullyAsyncRolloutFn` + `--max-weight-staleness`) is not wired in under ports. The adapter lists `--fully-async` as its own flag and forces it off. fully_async cannot colocate. Miles parses the weight version as a plain number (`common_filters.group_weight_version_stats` skips non-numeric values), but the version that ports writes to the inference engine is `yeto:<version>:<hash>`. So the Miles staleness filter does not take effect under ports.
      4. Four design points are decided (P0-S-Q1..Q4, 2026-10-13, see section 5 of COORDINATION.md). The implementation is written below (branch `s23-p0-s`, GPU run unverified).
    - P0-S implementation (10-13):
      1. **Evidence schema 4**: each trajectory records its own behavior policy (version, weight hash). The version of a trajectory is the oldest version among its tokens. When the version equals the current round, the hash must equal the hash of the current round. The version must not be newer than the current round. The batch hash and the trajectory ID move to a new domain (`yeto-trajectory-batch-v4`, `yeto-trajectory-id-v4`), so the batch hash changes and an old test run cannot be resumed. The ports `record_trained_groups` is the only write point and always writes schema 4 (the batch header contains `max_policy_age`). The legacy port still writes 1/2. Schema 3 is left for P2 (P2 merges first, and when this branch is rebased, 3 is added to the readable set).
      2. **The inference engine writes a plain numeric version**: before `update_weights`, the publisher uses a plugin to align the Miles weight version counter to `v-1`. After the update, the engine, the rollout executor and the counter all equal the yeto policy version `v`. The publisher then writes `"v"` once more and reads it back to check. The `yeto:<v>:<hash>` token stays only on the yeto side. The `PublishedPolicies` of the driver records "version to weight hash". Before a publish, it checks whether the same version already maps to another hash (if yes, it rejects and does not touch the engine). It records the entry only after the publish succeeds. The driver translates the numeric version that a group reports back to the token. A version that is not published keeps its original value and is rejected. The driver gives the rollout side (a metadata sink) the mapping inside the policy age window, and the evidence takes the hash of an old version from it. The Miles parsing of the version is not changed. So `--max-weight-staleness` works, and the Miles check that "the version of a full-parameter sample must be numeric" also passes.
      3. **Overlap of rollout and training**: with `--rl-max-policy-age N>0` and partitioned placement, ports sends `--fully-async --max-weight-staleness N`. It no longer sends the all-samples hook and the buffer filter (Miles fully_async does not support the former). Under fully_async, `record_trained_groups` reports the metadata of this round directly. Colocated placement still uses the original `--partial-rollout` continuation. The driver loop is unchanged: while round r trains, Miles keeps generating with v_r in the background. A group that `generate(r+1)` fetches may come from v_r, and the existing policy age check lets it pass. Full-parameter islands (SAO streaming) no longer reject `--rl-max-policy-age > 0`. The dense strict sweep still requires 0 (the whole round publishes in sync with the syncer, which is outside P0-S).
      4. **Cut point and resume** (after the review rework, 10-13): under fully_async, `fully_async_prompts.PromptLedger` wraps the data source inside the rollout executor process. It records each prompt group that was taken out, not yet trained, and not returned to the data source. At a cut point, the background workers stop first. Then these groups (in flight, and completed in the output buffer but not trained) are reset and put back into the data source buffer. A group that Miles judged stale and recycled is already in the buffer. The cut carries them away through the existing buffer path, and they are generated again after resume, so no prompt is lost. The data cursor does not roll back: fully_async trains in completion order and has no single roll-back point, so the untrained groups are carried back by the buffer. A generation task that still runs changes the original sample, and what is put back into the buffer is a copy. Without a ledger, the cut is rejected.
      4b. **Group counts under overlap**: each round reports `submitted_groups` (groups taken from the data source in this round) and `stale_dropped_groups` (stale groups that Miles dropped in this round). When Miles does not provide the latter, it is recorded as unknown (`None`) and a warning is raised. Under overlap, groups taken in this round finish in later rounds, so there is no per-round balance "submitted = completed + filtered + dropped in flight".
      4c. **Trade-off of recording only the oldest version in evidence**: the tokens of one trajectory may span two versions. The evidence records only the oldest version and its hash. Reason: the policy age limit is judged on the oldest version, so this record is enough to prove "not over the limit". The version segments per token are already handled by the weight version interval of Miles and the TIS correction. Putting them in the evidence would make the envelope larger and couple it to the internal format of Miles. Cost: the evidence alone cannot restore the generation version of each token. The schema 4 batch header also records `max_policy_age`, and on read it checks that the version difference of each trajectory does not exceed it.
      4a. **Behavior change (P0-S-Q5, decided by the main agent on 10-13)**: overlap is derived automatically from "N>0 + partitioned placement". No flag is added. So a run with LoRA partitioned placement + N>0 changes from `--partial-rollout` continuation to Miles fully_async. Colocated placement and N=0 do not change.
      5. **Not done**: the verl side (fully_async / `staleness_threshold`) is not wired this week, see the follow-up item of tasks 1.7b.3. Full-parameter colocated + N>0 goes through `--partial-rollout`, and its GPU behavior is not covered by local tests.
      6. **GPU run verification plan (merged into P0-1.11 GPU run)**: a small model with two LoRA islands, partitioned placement, `--rl-max-policy-age 1` against strict (0), same data and same seed. Criteria: (1) both groups finish the set number of rounds, with no `PolicyIdentityError` and no publish rejection. (2) For the N=1 group, the Miles metric `rollout/fully_async/*` shows that background generation overlaps with training (the queue is not empty during training in each round), and the maximum version difference of selected groups is <=1. (3) The evidence of each round is schema 4, contains trajectories of version r-1, and their hash equals the published hash of r-1. (4) The weight version read back from the engine equals the policy version of the driver. (5) The wall-clock time of each round of the N=1 group is lower than the strict group, and the reward curve is of the same magnitude as the strict group (bitwise equality is not required). (6) Resume once from a mid-run cut point: after resume, no old background trajectory enters training. The GPU run for full-parameter N>0 is scheduled separately.

## Risks / Trade-offs

- Phase 1 needs three minimum-card GPU runs for the baseline and the regression. The budget comes from the GPU ledger. Before a GPU run, write the review conclusion per memory gpu-review-before-launch.
- Moving `generate_rollout` first and splitting later leaves one larger module (the body and its exclusive helpers) for a short time. But it removes the legacy directory and the pin, which fits the PM starting point. The split continues in Phase 4.
- The bridge merge removes about 1000 lines. If the cross-check finds that the two delta math copies differ (for example, the merge_alpha handling of decoupled), the work must stop.
- Generating the config schema moves the definition place of 106 flags, so the diff is large. The comparison of the generated argument list is the safeguard.
- In the local test set, `mismatch_tape` and `upstream_parse_args`, which start a local Ray, are excluded.
