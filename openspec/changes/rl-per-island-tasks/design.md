# Design

## Flag format

`--rl-island-tasks` takes a string or a file path:

- String: `l0=web1-10,pwn1-10;l1=web11-20,pwn11-20`. The island key is `l{id}` or `{id}`, the same key rule as `launcher.py:2963 learner_image_for`.
- A range `web1-10` expands to `web1` through `web10`. The expansion rule accepts only "prefix + start and end integers".
- File: a JSON object `{"0": ["web1", ...], "1": [...]}`.

The parse function lives on the launcher side, not in `island_overrides.py`. Reason: `island_overrides.py` requires `--rl-negative-test-run` and is used only for negative-test runs (module docstring). It is not suitable for a production flag.

## Data flow (Q1 recommendation A)

```
cli --rl-island-tasks
  -> launcher parses, expands, validates
  -> per island: write_prompt_data(catalog, out, task_ids)  [local machine]
  -> per island --data <mount path>; the run manifest records task_ids and sha256
  -> inside the island, island_entry.prepare_prompt_data reads the local JSONL as usual
```

Without `--rl-island-tasks`, behavior does not change.

## Validation

1. Island numbers must be in `0..N-1`, and every island must have a list (a partly missing island is not allowed).
2. Every task id must be in the catalog.
3. Unequal task counts between islands: give a warning only, the same for strict and elastic (Q2 decided).
4. dense-full / SAO: allowed (Q5 decided to open up the data comparison).

## Contract hash

- LoRA ports: `session_contract_hash` contains no data, so no change is needed (verified by reading code).
- Full parameter (dense / expert-full): the training contract hash is compared across islands. The v5 of P0-1.7b.4 already removed the training data (`--data`, revision, `--prompt-data`). This change bumps it to v6 and also removes eval: the `evaluation` section in the contract is deleted, and the eval flags in the Miles argv (`--eval-prompt-data`, `--eval-interval`, `--n-samples-per-eval-prompt`, `--eval-temperature`, `--eval-top-p`, `--eval-max-*-len`, `--skip-eval-before-train`, `--log-passrate`) are listed as island-local. Reason: eval does not change the training weights; Q3 decided that eval runs only on the eval island. v6 also contains the change of P4 (rl-mixed-island-placement): when `--rl-island-placement` is given, the placement parameters also stay out of the contract, and the contract records `per_island_placement` separately (P4-Q6; after the merge, the version is bumped only this once). v6 changes all full-parameter contract values, so old test runs cannot resume (same as P0-D5, accepted).
- SAO: the contract comes from the external finalize manifest and does not contain the `--data` of this island, so it is not changed.

## Risks

- When task difficulty is unequal, elastic weighting leans toward the easier islands. This change only records it and does not correct it.
- Resume: a restarted island must get the same prompt file. The run manifest records the sha256, and the island compares it at start.

## Implementation notes (2026-10-13, P3 sub-agent)

1. **Source of the task list**: the launcher does not call `rlf/catalog.write_prompt_data`. It filters the `--data` JSONL line by line. The task id of each line comes from `metadata.task_id` (that is what `prompt_rows` writes), or from the top-level `task_id` if there is none. Reason: the launcher on the local machine does not need the RLF task package and admission evidence; any JSONL with task ids can be used; a prompt file generated by the `catalog` CLI can be used directly as `--data`. This requires `--data` to be one local `.jsonl` file, and every line must have a task id.
2. **Range expansion**: `<prefix><a>-<b>` expands to `<prefix>a` through `<prefix>b`; if the start number has leading zeros, the numbers are zero-padded to its width. If the whole token is itself a task id in the data, it is taken literally (for example `cve-2021-4`).
3. **Validation** (before cards are opened, `launcher._check_island_tasks`): `--data` must be a local JSONL; `--external-learners` is not supported; the launcher rejects an island number out of range, an island with no list, a duplicate task in one island, a task id not in the data, a reversed range, and a line without a task id. Unequal task counts give a warning.
4. **eval (Q3)**: when `--rl-island-tasks` is given, the launcher rejects `--rl-eval-interval` (training islands do not run eval; eval runs on the eval island with the full set).
5. **Two hops through the head**: the JSON file form is rewritten to the inline form on the first hop, and the launcher on the head regenerates the same bytes with the staged `--data`.
6. **Delivery**: the file of each island is written to `<run dir>/island-tasks/island-<id>.jsonl` and mounted at the mount point of the original `--data`; the island command gets `--data-sha256`. Lines keep the order and bytes of the source file; the same input gives the same hash.
7. **Records**: `run_manifest.json` gets `island_tasks` (island number -> `task_ids`, `data_sha256`); each island in the dry-run gets `island_tasks`; before training, the island checks the SHA256 of the file (on a mismatch it reports both values and refuses), and writes the same two fields into `rl_driver_start.island_tasks`.
8. **Flags**: the neutral CLI flag `--rl-island-tasks` is in `yeto/rl/engine/run_flags.py`; the island flag `--data-sha256` is in `yeto/rl/adapters/miles/run_flags.py`, next to `--data`. The parse and filter logic is in the neutral module `yeto/rl/island_tasks.py`.
9. **Not verified on GPU**: the island-side check and the `rl_driver_start` field have only local tests; see section 4 of tasks.md.
10. **Review rework (2026-10-13)**:
    - The task plan is computed only once per launch: `_check_island_tasks` computes it and caches it in `args._island_task_plan`; building island tasks, `run_manifest.json`, and the dry-run all read the cache. The cache is not part of the head replay arguments; the second hop on the head recomputes it itself; a test checks that the per-island SHA256 is the same on both hops.
    - Islands are built only from `--gpu` entries; elastic adds no island (P5 does not build an add-island CLI), so learner_id does not go beyond the plan. If a learner_id outside the plan is requested, the launcher reports an error and lists the island numbers in the plan.
    - A non-ports path (SFT learner, diffusion sample) that is given `--rl-island-tasks` is rejected directly.
    - The flag name in the error messages of `yeto/rl/island_tasks.py` is passed in by the caller.
    - The path of the JSON spec file must not contain `=` (a path with `=` would be parsed as the inline format); this is written in the help.
