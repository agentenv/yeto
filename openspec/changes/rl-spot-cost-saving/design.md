# Design：rl-spot-cost-saving

动机见 proposal.md。宽限期统一口径见 `rl-infra-spec/cloud-pool-design.md` §3.6（10-09 已核原文）。

## Context

- 岛结构：yeto 的一个岛今天是"训练＋生成同岛共置"（Miles colocated）。`yeto/rl/adapters/miles/placement.py:272-285` 对 `rollout_external`、`debug_rollout_only` 直接拒绝。跨岛样本传输未实现（agentic-rollout-utilization 阶段 3 因此不做两岛）。所以 yeto 目前**没有独立推理岛**。
- 已有的、不持训练唯一状态的岛：评测岛（`yeto/cloud/modal_eval_island.py`，Modal，被抢占后重启并按"版本+题号+第几次"续跑，eval D11）。
- elastic 模式下，每个训练岛把增量交给 syncer，离开时只丢自己未提交的增量（M1、V2 真机验证）。所以在 ≥2 岛的 elastic 运行里，某个岛被回收只损失它这一轮的工作，权重以 syncer 为准。
- 重开：`FleetController`（`yeto/launcher.py` 约 5825 行起）恢复失败岛时只在原云原区域重开（约 5832-5842、6294 行）。`cloud-pool-design.md` §4.1 有 `replace` 动作设计，未实现。
- 回收通知：仓库里没有代码读 AWS 实例元数据，也没有代码处理 Modal 中断信号（cloud-pool-design §6）。
- 已真机验证的底层能力：续训切点（G2、N15）、整岛离开重入（M1、V2）、重入数据位置（#149）、agentic 续跑与带在途轨迹的切点（#166）。

## Goals / Non-Goals

**Goals:** 云能力表与回收通知接口；推理型岛用 spot 并能换区域换云重开；回收时保存在途轨迹并续跑；成本打分；自动开卡开关。

**Non-Goals:** 训练岛用 spot（条件见 spec，第一版实际不满足）；节点级扩缩（G4/G6/G11）；跨卡型合并（去耦合 7.7 第二期）；自有集群；估计回收率。

## Decisions

**D1 "推理型岛"在 yeto 里分三期对应三种东西。**
- 第 1 期 评测岛：已存在、不持训练状态，直接可放 spot。Modal GPU 函数本来就不能设为不可抢占（Modal 抢占文档），所以评测岛在 Modal 上实际已经是"可抢占"的。本期补的是：能力表、通知处理、回收事件、换云候选。
- 第 2 期 elastic 可丢弃岛：在 ≥2 岛 elastic 运行里，除一个"锚点岛"（按需，保证总有岛在训练）外，其他岛标为可丢弃并允许 spot。它们持有训练副本，但权重以 syncer 为准，离开只丢本轮增量。严格说它仍是训练岛（I1），这里把它归为"损失有上界的 I1"，前提是：elastic、至少一个按需锚点岛、本岛离开后 syncer 不停。这是对 RLBoost"训练按需、生成 spot"的近似，不等价。是否接受此近似列为待用户拍板（见 Open Questions）。
- 第 3 期 独立推理岛：等价于 RLBoost。前置条件：①Miles 放开 `rollout_external`，训练岛把权重推给外部推理引擎；②跨岛样本传输（推理岛把轨迹送回训练岛，带版本段）；③推理岛权重拉取。这三项都不在本 change 实现，本 change 只写接口与前置检查，另开 change。
- 备选：直接做第 3 期。不选，因为三项前置都要改 Miles fork 与协议，工作量大且未验证，而第 1、2 期复用已验证能力即可先省钱。

**D2 云能力表先静态、后接口。** 表放在 `yeto/cloud/` 下的一个数据文件，字段见 spec。去耦合 8.1 的 `CloudProvider` 能力声明落地后直接读此表，不重复维护。本 change 与去耦合 8.x 的关系：8.1、8.5 保留（接口）；8.6 调度建议的打分公式以本 change D5 为准；8.7（回收接缝）由本 change 替代，在去耦合 tasks 里标"由 rl-spot-cost-saving 替代"。

**D3 回收处理放在岛内一个监听器里，按云取通知。** Modal：在岛入口注册退出处理（只做"设标志＋限时保存＋离开"，总时长上限取 30 秒减 5 秒余量）。AWS：岛内后台线程每 5 秒查实例元数据。两者都汇入同一个"回收通知"事件，后续顺序统一（spec「回收通知处理顺序」）。离开复用 elastic LEAVE；非 elastic 的评测岛走评测续跑记账。

**D4 换区域换云。** `FleetController` 的恢复路径改为：先问候选生成器（读能力表、容量探针、兼容组、权重所在位置），按 D5 排序取第一个；开关关闭时只写建议。候选生成与打分是纯函数，可单测。跨云还要满足 cloud-pool-design §4.2 的五个前提（能连协调器、权重已在该云、存储、镜像、数值口径）。

**D5 成本打分。** 分数 = 单价÷有效算力 ＋ 准备成本÷预计停留时长 ＋ 回收期望损失。准备成本优先用 `pool_grow` 实测，没有就用 cloud-pool-design §5.3 保守上界。回收期望损失 = 回收率 × 每次损失。回收率来自本 change 的回收事件汇总；同一云区域少于 3 次记录时记"未知"，不参与排序，只列风险（cloud-pool-design §7.1 第 4 条建议）。阈值 3 是拟定值，无实测依据，待数据积累后调整。

**D6 自动开卡开关。** 默认关（去耦合 D10 要求用户确认）。打开需要显式参数并同时给出本运行预算上限。每次自动开卡前查预算，写事件。

**D7 在途轨迹续跑。** 复用 #166 的带在途轨迹切点格式与 started_rollout_id / policy_versions 字段，不新造格式。回收路径与正常切点的差别只有两点：限时（超时的轨迹记丢弃）与写到持久存储（而不是本地）。agentic：只在回合之间挂起，沙箱不跨云保活，换云后能重放工具调用就重放，否则丢弃。体积估计：0.6B 级在途轨迹每条 KB 到 MB 量级，写 Modal 卷是否进得了 25 秒未测，列为上卡测量项。

## Risks / Trade-offs

- [Modal 30 秒包括写卷与 commit，v1 卷 commit 实测 23–35 秒（10 GiB）] → 在途轨迹只写小文件；实测超时就改为"只写中断标记"，续跑退化为丢弃重做。
- [AWS 通知尽力而为，可能没有通知就被停] → 按"机器没了"走租约过期路径，损失按事件记。
- [第 2 期可丢弃岛不是真正的训练/生成分离，省钱幅度小于 RLBoost] → 第 2 期上卡时实测并如实报告，不引用 RLBoost 数字作为 yeto 结果。
- [换云需要权重已在目标云] → 候选生成器把复制成本计入准备成本，不在目标云就排后。
- [自动开卡出错导致花钱] → 默认关；预算上限硬检查；所有开卡写事件。

## Migration Plan

全部新增，默认行为不变（开关默认关、无 spot 标记的岛照旧）。回退：关掉开关、去掉可丢弃标记即可。
