# EXP2.16: Repeated-Anchor Batch-Consensus Policy Search

## Question

Does repeated anchor evidence rescue deployable action selection?

EXP2.14 and EXP2.15 showed that single anchor-split action ranking is nearly random against a disjoint oracle split. This experiment takes the suggested step back: do not pick the anchor top-1 action directly. Instead, act only when the same action shows repeated paired improvement over `token_weighted` across saved anchor batches; otherwise fall back to `token_weighted`.

This is still an offline replay. No online training was started.

## Policy Family

The deployable actions are:

```text
token_weighted
freshness_weighted
anchor_drop_bottom25
anchor_positive_threshold
anchor_shrink
probecommit_v1
```

Oracle policies are not selectable. They are used only for evaluation in the replay records.

For each non-token action, the script computes paired anchor-batch gains:

```text
d[action, batch] =
  action_anchor_batch_utility[batch]
  - token_weighted_anchor_batch_utility[batch]
```

It then searches conservative held-out-seed policies based on:

```text
gain_mean
gain_se
gain_lcb = gain_mean - k * gain_se
win_rate = fraction of anchor batches with d > 0
subset_top_frac = fraction of half-anchor subsets where action is top
selected_mass
```

The policy variants are:

```text
paired_lcb
mean_gain_and_consensus
batch_consensus_lcb
batch_consensus_mean
safe_shrink
```

The important change from earlier action-probe policies is that this search is not asking "which action has the highest noisy anchor mean?" It asks a weaker and more realistic question:

```text
Is any deployable action repeatedly better than token_weighted on anchor batches?
```

If not, it defaults to `token_weighted`.

## Step-Back Interpretation

This result is important because it closes the obvious escape hatch after EXP2.14:

```text
"Maybe one anchor split is noisy; repeated anchor consensus will fix action selection."
```

It did not. The repeated-anchor policies are safer than raw top-1 in the sense that they mostly avoid catastrophic mass dropping, but they do not reliably improve one-step merged-update utility.

The current evidence chain is now:

```text
1. Equal-token fragments have diverse current-state utility. Passed.
2. Bad candidates measurably affect merged updates. Passed.
3. Oracle deployable actions have headroom. Passed.
4. Candidate-level anchor-gradient can predict individual utility. Partially passed.
5. Anchor/probe measurements can select group-level actions. Failed.
6. Repeated anchor-batch consensus can select group-level actions. Failed.
```

That points to a more specific failure mode:

```text
The problem is not only noisy candidate scoring.
The problem is that local one-step probe measurements do not transfer reliably to group-level action ranking under the current capture/evaluation design.
```

## Existing-Work Implications

A literature pass suggests we should stop treating this as a pure winner-selection problem. The most relevant directions are:

| Prior idea | Implication for next experiment |
|---|---|
| Async Local-SGD / delayed Nesterov | Correct stale pseudo-gradients at the outer optimizer instead of picking winners. |
| HeLoCo-style stale block correction | Shrink or project stale/conflicting blocks rather than reject whole actions. |
| Delay-compensated ASGD | Use age and a cheap curvature/second-moment proxy to compensate stale deltas. |
| FedBuff / BASGD | Buffer before commit; do robust/soft aggregation with timeout instead of immediate top-1 selection. |
| Robust aggregation | Test clipped mean, trimmed mean, median-like block aggregation as baselines. |
| Zeno-style validation | If probing is used, probe candidate or buffer descent directly, but account for high variance and probe/oracle split mismatch. |

This changes the next policy target:

```text
Do not ask "which action wins this group?"
Ask "can the syncer reduce harm with soft stale correction, buffering, and robust aggregation without relying on brittle top-1 action ranking?"
```

## Decision

Do not start online ProbeCommit from the current action-selection family.

The result is not "the project is dead." The measurement result remains strong: harmful equal-token fragments exist, bad mass affects merges, and oracle headroom exists on both SmolLM2 and Qwen3.5-9B. The negative result is narrower:

```text
group-level deployable action selection from current anchor-probe measurements is not working.
```

## Next

The next offline work should pivot away from action selection and toward soft correction/buffering:

1. Implement offline buffered robust aggregation replay.
2. Include `token_weighted`, `age_decay`, `norm_clipped_mean`, `trimmed_mean`, `blockwise_cosine_shrink`, and `delayed_nesterov_proxy` policies.
3. Evaluate them against token-weighted and oracle upper bounds on the same SmolLM2 and Qwen3.5-9B artifacts.
4. Only consider online training if a non-oracle soft policy gets positive held-out-seed gain and negative-rate reduction without dropping most mass.

This is the harder but more plausible route: make the syncer less brittle, not more clever at top-1 guessing.
