# EXP2.17: Soft Robust Syncer Replay

## Question

Can we make the default fragment merge harder to damage without relying on brittle group-level action selection?

EXP2.14-EXP2.16 showed that anchor/probe measurements do not reliably rank deployable actions. This experiment stops asking which action wins a group. It instead evaluates soft, non-oracle syncer rules that transform or robustly aggregate all candidates:

```text
token_weighted
uniform
age_decay
norm_clipped_mean
RDA after norm clipping
momentum conflict shrink
HeLoCo-style momentum correction
trim largest-norm candidate
medoid
```

This is an offline one-step replay on existing SmolLM2 tensor artifacts. No online training was started.

## Inputs

Local tensor/state artifacts exist for SmolLM2:

```text
experiment-results/EXP2/equal-token-late-smollm2-p4de-seed53-syncer-current-6m/work/m12/syncer_probe/
experiment-results/EXP2/equal-token-late-smollm2-p4de-seed67-syncer-current-6m/work/m12/syncer_probe/
experiment-results/EXP2/equal-token-late-smollm2-p4de-seed79-syncer-current-6m/work/m12/syncer_probe/
```

Qwen3.5-9B dense currently has only scalar replay artifacts locally; its raw `candidate_f32` and `state_before_step_*.ckpt` files were not pulled back. Therefore Qwen cannot yet run this tensor-level replay without restoring those payloads.

## Implementation

New scripts:

```text
scripts/replay_soft_robust_syncer.py
scripts/aggregate_soft_robust_syncer.py
```

The replay script loads each captured pre-merge syncer checkpoint, reads candidate fragment tensors, constructs a trial merged fragment for each policy, applies it to the model, and evaluates fixed probe loss.

Important implementation detail:

```text
update = candidate_fragment - current_fragment
```

This matches the Python replay convention: a trial merge is `current + update`. For HeLoCo-style correction, the script converts to the Rust syncer convention internally:

```text
delta = current_fragment - candidate_fragment
```

then applies the correction against syncer momentum and converts back.

## Policies

`token_weighted`: current baseline.

`uniform`: equal candidate weights.

`age_decay_tau4`, `age_decay_tau8`: token weights multiplied by `exp(-age / tau)`.

`norm_clip_m1`, `norm_clip_m15`: clip candidate update norms to `median(norms) * {1.0, 1.5}` before token-weighted averaging.

`rda_clip_m1`, `rda_clip_m15`: apply the same clipping, then radial-directional averaging.

`momentum_shrink_mild`, `momentum_shrink_medium`: shrink update magnitude based on conflict with current syncer momentum direction.

`heloco_avg`, `heloco_rda`: HeLoCo-style momentum correction before averaging or RDA.

`trim_norm_high1`: remove the largest-norm candidate, then token-weighted average. This is diagnostic only if selected mass falls too low.

`medoid`: choose the candidate whose update is closest to the other updates. This is also diagnostic only because selected mass is very low.

## Smoke Validation

I first ran a 3-group CPU smoke test on seed 53. It produced nonzero losses and policy differences.

I also tried `--device mps`, but the probe weights became corrupted after transfer to MPS and the replay returned zero or nonsensical losses. Therefore the local runs below use CPU. This is slow but valid for small offline samples.

## Interpretation

This does not pass the online gate.

The only policies with positive aggregate mean gain are low-mass or unsafe:

```text
medoid:
  mean gain positive, but selected mass is only 0.154 and only 1/3 seeds is positive.

trim_norm_high1:
  positive on all three seeds and improves strict-negative rate,
  but selected mass is only 0.846 and negative-rate worsens.
```

The high-mass policies are mostly no-op or slightly negative:

```text
norm_clip_m1:
  almost neutral, selected mass 1.0, mild strict-negative improvement,
  but aggregate mean gain is slightly negative.

heloco_avg:
  selected mass 1.0 and strict-negative improvement,
  but aggregate mean gain is negative.

RDA variants:
  worse on this screen.
```

This result is useful but not good enough:

```text
soft robust one-step policies are less brittle than action-probe top1,
but the current unbuffered variants do not yet produce a high-mass,
seed-stable win.
```

## Decision

Do not go online.

Continue the policy-rescue path only with buffered robust aggregation, because the unbuffered robust policies have too few candidates per group to make robust statistics work cleanly.

The current best next test is:

```text
buffered_norm_clipped_mean
buffered_norm_winsorized_rda
buffered_norm_clipped_mean + age_decay
```

The key hypothesis is now narrower:

```text
buffering may give enough effective candidates for robust aggregation,
whereas unbuffered m12 groups are still too small/noisy.
```

## Exact Commands

Seed 53:

```bash
.venv/bin/python scripts/replay_soft_robust_syncer.py \
  --capture-dir experiment-results/EXP2/equal-token-late-smollm2-p4de-seed53-syncer-current-6m/work/m12/syncer_probe \
  --model HuggingFaceTB/SmolLM2-135M \
  --data experiment-results/EXP2/equal-token-late-smollm2-p4de-seed53-syncer-current-6m/work/eval.jsonl \
  --seq-len 128 \
  --lora-r 2 \
  --lora-alpha 4 \
  --fragments 12 \
  --probe-batches 2 \
  --probe-batch-size 1 \
  --probe-max-rows 64 \
  --train-on all \
  --device cpu \
  --max-groups 24 \
  --progress-every 8 \
  --out-jsonl experiment-results/EXP2/soft_robust_syncer/seed53/soft_robust_24.jsonl \
  --out-summary experiment-results/EXP2/soft_robust_syncer/seed53/soft_robust_24_summary.json
```

The same command was repeated for seeds 67 and 79 with the corresponding paths.
