# EXP2.10: Anchor Stability Sweep

## Question

EXP2.9 failed to choose useful group-level merge actions from a two-batch anchor probe, even though oracle replay showed large deployable action headroom. EXP2.10 asks a narrower follow-up:

```text
Is EXP2.9 failing mainly because the anchor probe is too small/noisy?
```

The specific test is whether increasing anchor evidence from 2 to 4 to 8 batches improves action ranking against the disjoint oracle split. This is also the immediate gate before spending larger-model compute.

## Setup

EXP2.10 reuses the existing SmolLM2-135M fixed-token freeze-delay captures:

```text
experiment-results/EXP2/equal-token-late-smollm2-p4de-seed53-syncer-current-6m/
experiment-results/EXP2/equal-token-late-smollm2-p4de-seed67-syncer-current-6m/
experiment-results/EXP2/equal-token-late-smollm2-p4de-seed79-syncer-current-6m/
```

No online training, new model capture, AWS job, or Gemma-scale run was started.

For each seed, I reran direct action-probe replay with:

```text
anchor_batches = 8
oracle_source = precomputed
anchor_deployable_only = true
include_anchor_batch_utilities = true
```

Then `scripts/analyze_action_probe_stability.py` derived repeated 2/4/8-batch anchor subsets from the saved per-batch utilities.

Deployable actions:

```text
token_weighted
freshness_weighted
anchor_drop_bottom25
anchor_positive_threshold
anchor_shrink
probecommit_v1
```

Reference actions are used only for evaluation and are never selectable.

## Gate Check

EXP2.10 does not pass:

```text
mean_gain_ge_0.0005: false
all_seeds_positive: false
negative_drop_ge_0.20: false
strict_drop_ge_0.20: false
headroom_captured_ge_0.40: false
seed67_nonnegative_headroom: false
gate_pass: false
strong_pass: false
```

The key diagnostic is:

```text
2 -> 4 -> 8 anchor batches does not improve group-level action ranking.
```

This weakens the hypothesis that EXP2.9 failed only because the anchor split was too small. More anchor batches reduce one source of noise, but the anchor/oracle action ranking remains near random at the group level.

## Decision

Do not start online ProbeCommit from the current action-probe design.

Do not start a Gemma-scale run as the immediate next step. Larger models may still change the utility signal, but EXP2.10 does not provide a clean reason to spend that compute yet. The current blocker looks more structural than a simple two-batch noise issue:

```text
bad merge headroom exists,
deployable oracle action headroom exists,
but deployable action selection remains unstable even with 8 anchor batches.
```

The next harder test should be a bounded model-scale diagnostic only after redesigning what is measured. It should answer whether scale improves anchor/oracle action-rank agreement, not whether a larger model can mask the current policy weakness.

## Recommended Next Work

1. Add an action-stability capture mode that stores several independent anchor splits, not only eight adjacent anchor batches from one fixed split.
2. Increase oracle reliability before scale-up: 16 oracle batches and larger oracle row pool for a smaller number of groups.
3. Add temporal or replay-depth structure: compare action ranking at stale replay depths `0, 1, 2, 4, 8`.
4. Add disagreement features that are action-level rather than candidate-level: candidate covariance, merge delta norm, action pair deltas, and predicted action utility variance.
5. Only then run a bounded larger-model diagnostic with 200-400 complete groups and the same action-rank metrics.

If a larger-model diagnostic is run later, the pass criteria should be:

```text
top1 action agreement >= 0.35
pairwise action-rank concordance clearly above 0.55
margin-gated or risk-aware gain >= 0.0005
negative-rate drop >= 0.20
all splits positive
```
