# EXP2.23: Vanilla-Schedule Synchronous Control

## Question

Are the high negative-merge rate and the outer-momentum damage measured in
EXP2.19-EXP2.22 caused by asynchrony (staleness from the injected
0/800/1600/2400 ms delays), or are they inherent to the DiLoCo-family
mechanism of merging independent local-SGD updates?

The test removes every injected delay while keeping the model, data, seeds,
strict schedule, and measurement tooling identical, giving a synchronous
"vanilla-schedule" counterpart to the async seed-223 captures.

## System

```text
provider: Verda (ex-DataCrunch) spot, FIN-01, 4x A100 SXM4 80GB
model: Qwen3.5-9B, LoRA rank 2 / alpha 4
data: trl-lib/Capybara, 5000 train rows / 64 eval rows
learners/fragments/quorum: 4/4/4, strict, 80 outer groups
local window: 8192 tokens / 64 microsteps
delays: 0/0/0/0 ms, jitter 0 (async comparators: 0/800/1600/2400 ms, jitter 50)
delta correction: none
shuffle seed 223, training seed 223223, token budget 700k
code commit: 46ed83c
python 3.10.12, torch 2.5.1 cu121, transformers 5.13.0
```

Two arms, run sequentially on the same node from byte-identical materialized
data:

```text
sync-sgd028:      outer SGD (nesterov mu=0), LR 0.28  — sync counterpart of
                  qwen9b-locked-noheloco-sgd-lr028-seed223-700k
sync-mu09-lr175:  outer Nesterov mu=0.9, LR 0.175      — vanilla-DiLoCo
                  optimizer under the same zero-delay schedule
```

Both arms completed 80/80 strict full-quorum groups with 20 commits per
fragment and zero transport or config failures.

## Caveat On "Synchronous"

Learners do not hard-block at a barrier: they continue local optimization
while a commit is in flight, exactly as in the async runs. With zero injected
delay, staleness is bounded by commit latency (tens of milliseconds) rather
than exactly zero. This is "vanilla schedule," not a lockstep DiLoCo
implementation. The optimizer design point also differs from the DiLoCo
paper (H around 500 full-finetune steps there; 64-microstep LoRA windows
here), so the momentum result is a claim about this cadence.

## Primary Result: Negative Merges Are Not Caused By Asynchrony

The exact-LR replay (`replay_exact_lr_probe.py`) was run on the sync SGD
capture with the identical multiplier grid, anchor (256 rows at source
offset 11,000, SHA-verified against the EXP2.22 manifest), disjoint oracle
(512 rows at offset 12,000), and selector thresholds as EXP2.21.

| Schedule, seed 223, SGD-0.28 | Negative-merge rate | Mean scalar oracle headroom |
|---|---:|---:|
| async 0/800/1600/2400 ms | 0.3625 | 0.001807 |
| sync 0/0/0/0 ms | 0.3875 | 0.001995 |

(Async seed 239: negative rate 0.2875, headroom 0.001834.)

Removing all injected staleness does not reduce the negative-merge rate
(the two-group difference is within noise at n=80). The one-step damage and
the scalar oracle headroom are properties of merging independent local-SGD
trajectories, not of the delay injection.

The EXP2.21 selector phenomenology also transfers unchanged to the sync
capture:

```text
recorded x1-fallback selector: selection rate 0.1625,
  gain vs x1 = 0.001073, oracle headroom captured 53.8%
best fixed multiplier: 1.5, gain 0.000998
(async seed-223 values: 0.2125, 0.001009, 56.1% aggregate, 0.000963)
```

## Secondary Result: Momentum Damage Is Not Async-Specific

| Arm | Eval loss (64-row) | Wall time |
|---|---:|---:|
| sync SGD LR 0.28 | **1.359852** | 1,470 s |
| sync Nesterov mu=0.9, LR 0.175 | 1.419274 | 1,436 s |

Vanilla DiLoCo's mu=0.9 is `0.0594` worse than scale-matched memoryless SGD
with zero injected delay — as large as or larger than the async-schedule
penalty measured in EXP2.19. Tape geometry shows the same pathology as the
async captures:

| Arm | Step norm mean | Direction cosine | History/current |
|---|---:|---:|---:|
| sync SGD-0.28 | 2.869 | 1.000 | 0.000 |
| sync mu=0.9 | 4.025 | 0.797 | 0.685 |

## Tertiary Result: Asynchrony Is Nearly Free Here

Sync SGD-0.28 ends at eval loss `1.359852`; the async seed-223 SGD-0.28 run
recorded `1.359505`. The 0-2400 ms delay pattern changes the endpoint by
about `0.0003` at this horizon — negligible relative to the optimizer and
policy effects under study.

## Interpretation

1. The ~32-39% negative one-step merge rate and the ~0.002 scalar oracle
   headroom are DiLoCo-family-inherent (local-update interference plus
   stochastic one-step noise), not artifacts of the async harness.
2. The outer-momentum pathology is a cadence/config property, not a
   staleness interaction. Short-window LoRA training does not want mu=0.9.
3. What remains unattributed is the single-worker noise floor: a lone
   learner's steps would also sometimes look negative on a 512-row oracle.
   Separating "merge interference" from "any stochastic step" requires a
   single-learner control; per-candidate solo utilities are computable
   offline from the retained sync captures.

## Known Limitations

1. One seed, one model/data configuration, 80 groups per arm.
2. Zero-delay strict quorum approximates but does not equal lockstep
   synchronous DiLoCo (no learner barrier).
3. The mu=0.9 arm uses the project's tuned LR 0.175, not the DiLoCo paper's
   0.7 at its much longer sync interval.
4. Different hardware (Verda A100-80GB) and driver stack than the AWS
   p4d A100-40GB async runs; rates and losses compare, bytes do not.
5. The exact-LR replay is exact only for memoryless SGD; the mu=0.9 arm was
   therefore assessed via endpoint loss and tape geometry, not replay.

## Exact Command Shape

```bash
python scripts/compare_diloco.py \
  --model qwen35-9b \
  --data trl-lib/Capybara \
  --settings m4 \
  --baseline-loss 0.0 \
  --delta-correction none \
  --outer-optimizer nesterov \
  --outer-lr {0.28|0.175} \
  --outer-momentum {0|0.9} \
  --token-budget 700000 \
  --seq-len 128 \
  --micro-batch-size 1 \
  --inner-lr 0.001 \
  --lora-r 2 \
  --lora-alpha 4 \
  --eval-rows 64 \
  --max-rows 5000 \
  --shuffle-rows-seed 223 \
  --training-seed 223223 \
  --device cuda \
  --gpu-slots 4 \
  --fixed-window-tokens 8192 \
  --fixed-window-microsteps 64 \
  --pad-to-fixed-window-tokens \
  --freeze-delta-before-delay \
  --learner-push-delay-ms 0,0,0,0 \
  --learner-delay-jitter-ms 0 \
  --syncer-total-steps 80 \
  --learner-max-steps 2500 \
  --strict-quorum \
  --syncer-probe-capture \
  --syncer-probe-capture-every 1 \
  --work-dir .../vanilla-sync-seed223/{arm}/work \
  --report-dir .../vanilla-sync-seed223/{arm}/report
```

The replay and aggregation used `replay_exact_lr_probe.py` /
`aggregate_exact_lr_probe.py` with the EXP2.21 grid
(`0.5,0.75,0.875,1.0,1.125,1.25,1.5`) sharded 4-way.
